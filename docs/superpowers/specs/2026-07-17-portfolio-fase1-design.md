# Gestione Portfolio — Fase 1: migrazione dati portfolio su database

**Contesto:** Silvia deve poter aggiungere nuove illustrazioni al portfolio da sola,
senza chiedere un redeploy. Oggi le ~126 immagini esistenti sono elencate in un file
di codice (`src/app/core/data/portfolio-manifest.data.ts`), organizzate per cartella
fisica sotto `public/images/`. Questa Fase 1 sposta tutti i **metadati** (titolo,
categoria, ordine) delle immagini esistenti nel database Supabase e ricablea la
pagina pubblica Portfolio per leggerli da lì — nessuna UI di amministrazione viene
costruita qui (Fase 2, da progettare a parte). I file immagine fisici **non vengono
spostati**: restano pubblicati da `public/images/...` come oggi, il database si
limita a referenziarne il percorso.

## Sezione 1 — Schema database

Nuova tabella `portfolio_immagini`:

```sql
create table portfolio_immagini (
  id bigint generated by default as identity primary key,
  src text not null,
  titolo text not null,
  categoria text not null,
  ordine integer not null default 0,
  pubblicato boolean not null default true
);

alter table portfolio_immagini enable row level security;

create policy "portfolio_immagini_select_pubblico"
  on portfolio_immagini for select
  to anon, authenticated
  using (true);
```

- `categoria` è testo libero, non un enum fisso: la Fase 2 permetterà a Silvia di
  digitare anche categorie nuove, quindi non ha senso vincolarle qui. Si salva
  direttamente l'etichetta leggibile (es. `"Elementi Botanici"`), non uno slug
  tecnico — evita una tabella di corrispondenza slug↔etichetta che altrimenti
  servirebbe solo a questo scopo.
- `ordine` esiste già da questa fase (anche se nessuna UI lo modifica ancora) perché
  la Fase 2 costruirà un riordino drag & drop che ha bisogno di un valore di
  partenza coerente per ogni immagine, non solo per quelle nuove.
- Nessuna policy di `insert`/`update`/`delete` in questa fase: la Fase 2 le
  aggiungerà quando servirà scrivere da un utente autenticato. La migrazione dei
  dati esistenti (Sezione 2) viene eseguita direttamente nell'SQL Editor, che non
  passa dalle policy RLS.

## Sezione 3 — Pagina Portfolio pubblica

**Nuovo modello** in `src/app/core/models/gallery-item.model.ts` (sostituisce
l'attuale, che aveva `category: GalleryCategory` fisso e un campo `featured` mai
letto da nessun template):

```ts
export interface GalleryItem {
  id: number;
  src: string;
  title: string;
  category: string;
  ordine: number;
}

export interface GalleryCategoryOption {
  value: string;
  label: string;
}
```

(`GalleryCategory` union type rimosso: le categorie non sono più un insieme fisso
conosciuto a compile-time.)

**Nuovo metodo** in `src/app/core/services/supabase.service.ts`, accanto a
`getPublishedEvents()`:

```ts
/** Immagini portfolio pubblicate, ordinate per categoria poi per ordine manuale. */
async getPublishedPortfolioItems(): Promise<GalleryItem[]> {
  const client = await this.getClient();
  const { data, error } = await client
    .from('portfolio_immagini')
    .select('*')
    .eq('pubblicato', true)
    .order('categoria', { ascending: true })
    .order('ordine', { ascending: true });
  if (error || !data) return [];
  return data.map((row) => ({
    id: row['id'],
    src: row['src'],
    title: row['titolo'],
    category: row['categoria'],
    ordine: row['ordine'],
  }));
}
```

**`portfolio.ts`**: `private readonly allItems = this.content.galleryItems;` (array
statico) diventa un segnale caricato in modo asincrono, con lo stesso pattern già
usato in `eventi.ts`/`home.ts`:

```ts
private readonly supabase = inject(SupabaseService);
protected readonly allItems = signal<GalleryItem[]>([]);
protected readonly itemsLoaded = signal(false);

// nel constructor, dentro afterNextRender:
this.supabase.getPublishedPortfolioItems().then((items) => {
  this.allItems.set(items);
  this.itemsLoaded.set(true);
});
```

Tutti i riferimenti a `this.allItems` nei `computed` esistenti (`filteredItems`,
ecc.) diventano `this.allItems()` (chiamata al segnale).

Le pillole filtro categoria non sono più `this.content.galleryCategories` (array
statico), ma calcolate dalle categorie effettivamente presenti tra le immagini
caricate:

```ts
protected readonly categories = computed<GalleryCategoryOption[]>(() => {
  const distinct = Array.from(new Set(this.allItems().map((item) => item.category)));
  return [{ value: 'tutte', label: 'Tutte' }, ...distinct.map((c) => ({ value: c, label: c }))];
});

protected readonly activeCategory = signal<string>('tutte');
```

(`setCategory(category: string)`: firma allargata da `GalleryCategory | 'tutte'` a
`string`, nessun altro cambiamento nel corpo del metodo.)

**`portfolio.html`**: la riga `@for (cat of categories; track cat.value)` diventa
`@for (cat of categories(); track cat.value)` (ora è un segnale). Il blocco che
contiene le pillole filtro e la griglia (dal separatore `<!-- Separatore -->` fino
alla fine della `<section>` con `id="galleria"`) viene avvolto in un controllo di
caricamento, sullo stesso modello di `eventi.html`:

```html
@if (!itemsLoaded()) {
  <p class="text-center text-gray-600 py-12">Caricamento galleria…</p>
} @else if (allItems().length === 0) {
  <p class="text-center text-gray-600 py-12">Nessuna illustrazione disponibile al momento.</p>
} @else {
  <!-- contenuto attuale: separatore + pillole filtro + griglia + paginazione, invariato -->
}
```

Lo stato vuoto "Nessuna illustrazione in questa categoria" (`@empty` sulla griglia,
per quando un filtro categoria specifico non ha risultati) resta invariato e
indipendente da questo.

**Effetto collaterale accettato**: l'ordine delle pillole filtro passa da quello
fisso di oggi (Composizioni, Animali, Elementi Botanici, Insetti) all'ordine
alfabetico delle categorie effettivamente presenti (Animali, Composizioni, Elementi
Botanici, Insetti) — non esiste più un concetto di "ordine fisso delle categorie"
una volta che sono libere e create da Silvia.

## Sezione 4 — Pulizia

- Rimuove interamente `src/app/core/data/portfolio-manifest.data.ts` (il suo
  contenuto vive ora nel database).
- Rimuove da `content.service.ts`: l'array `galleryItems`, `galleryCategories`, il
  metodo privato `buildGalleryItems()`, e gli import di `PORTFOLIO_RAW_FILES` e
  `titleFromFileName` (quest'ultimo resta usato solo dallo script di migrazione,
  non più dal codice applicativo — la funzione stessa in `text.util.ts` non viene
  toccata, resta disponibile se servirà in futuro).

## Cosa NON fa questa fase

- Nessuna UI per caricare, modificare, nascondere o riordinare immagini (Fase 2).
- Nessun upload di file: le immagini restano quelle già pubblicate in
  `public/images/...`.
- Nessuna modifica ai file fisici o alle cartelle sotto `public/images/`.
- Nessuna modifica alle pagine Eventi, Home, Shop o al pannello
  `gestione-prenotazioni` esistente.
